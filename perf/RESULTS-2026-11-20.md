# Read Throughput Baseline Benchmark Results

**Date of Execution:** 2026-11-20  
**Target Application:** School Store Backend Read Path (Public Catalogue & Authenticated Parent Orders)  
**Branch:** `perf/read-baseline` (branched from `release/guest-nosave-portal`)  

---

## 1. System, Runtime & Benchmark Environment

### Hardware Specification
- **CPU:** AMD64 Family 25 Model 117 Stepping 2, AuthenticAMD (16 Logical Processors / Cores)
- **RAM:** 16 GB Physical RAM
- **Operating System:** Microsoft Windows 11 Pro (x64, Build 10.0.26300)
- **Load Generator Location:** Colocated on the same physical host (`127.0.0.1`); generator process CPU usage was monitored and tracked independently to ensure the generator never saturated client-side resources.

### Software & Server Versions
- **Python:** 3.11.9 (64-bit)
- **Django:** 5.2.17
- **Database Engine:** SQLite 3.45.1 (`dev_db.sqlite3`) for local benchmark harness; production configuration targets PostgreSQL 16+ via `psycopg` 3.3.6.
- **Cache Backend:** Django `LocMemCache` for local benchmark harness; production targets `django-redis` with Redis 7+.
- **Application Server:** Waitress WSGI multi-threaded server configured with **16 worker threads** (`threads=16`), listening on `127.0.0.1:8000`.
- **Database Pool Configuration:** Rule P7 bounded pool defaults (`DB_POOL_MIN_SIZE=2`, `DB_POOL_MAX_SIZE=10`, `DB_CONN_MAX_AGE=60`).

### Test Dataset Size
- **Schools:** 16 schools across 212 registered cities (active branch networks in Surat & Ahmedabad).
- **Catalogue Products:** 48 base products.
- **Product Variants:** 230 active variants across 5 categories.
- **Students:** 796 students linked across classes and branches.
- **Synthetic Parents:** 50 parents created via `seed_perf_parents` with phones `5000000001`–`5000000050`, each with 1–2 children and 1–6 attached orders.
- **Orders:** 3,175 total orders in the database.
- **Total Database File Size:** 18.5 MB (18,874,368 bytes).

### Rate Limit & Throttle Overrides
To ensure that benchmark measurements reflect server throughput and database indexing rather than rate-limiting blocks (HTTP 429), the following overrides were injected into the test execution process environment:
- `PUBLIC_CATALOG_RATE = "1000000/min"`
- `LOGIN_THROTTLE_RATE = "1000000/min"`
- `OTP_THROTTLE_RATE = "1000000/min"`
- `STUDENT_CLAIM_USER_RATE = "1000000/hour"`
- `STUDENT_CLAIM_IP_RATE = "1000000/hour"`

> [!NOTE]
> No settings files were modified, altered, or committed in the git repository. All throttle overrides were applied purely through environment variables at runner invocation.

## 2. Benchmark Mix Definitions

### A. Public Catalogue Mix (`catalog`)
Models an unauthenticated guest or parent browsing the school store:
1. **25%** `GET /api/public/schools/` — School directory list.
2. **15%** `GET /api/public/states/` — State list.
3. **15%** `GET /api/public/cities/?state=Gujarat` — Cities filtered by state.
4. **15%** `GET /api/public/cities/{city_id}/branches/` — Active branches for a city.
5. **10%** `GET /api/public/grades/` — Grade / class list.
6. **20%** `GET /api/public/products/?school={school}&class={class}&gender={gender}` — Targeted product catalog with stock status flags.

### B. Authenticated Parent Orders Mix (`parent-orders`)
Models a parent logged into the mobile portal checking their orders:
1. **50%** `GET /api/orders/` — List own orders (scoped by parent, paginated, ordered by `-created_at`).
2. **30%** `GET /api/orders/{id}/` — Order detail with items, variant snapshots, and status history.
3. **20%** `GET /api/students/` — List linked children (beneficiaries).

## 4. Query Plan & Database Index Verification

### A. Parent Orders List Query (`GET /api/orders/`)
Query generated by Django ORM:
```sql
SELECT "orders_order"."id", "orders_order"."order_number", ...
FROM "orders_order"
WHERE "orders_order"."parent_id" = ?
ORDER BY "orders_order"."created_at" DESC;
```

**EXPLAIN QUERY PLAN Output:**
```
(4, 0, 0, 'SEARCH orders_order USING INDEX idx_order_parent_created (parent_id=?)')
```

**PostgreSQL Equivalent:**
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders_order
WHERE parent_id = '...'
ORDER BY created_at DESC;
```
Plan confirms that PostgreSQL performs an **Index Scan** using `idx_order_parent_created` on `(parent_id, created_at)` without any external Sort node.

### B. Parent Order Detail Query (`GET /api/orders/{id}/`)
Query generated by Django ORM:
```sql
SELECT "orders_order"."id", ...
FROM "orders_order"
WHERE ("orders_order"."id" = ? AND "orders_order"."parent_id" = ?);
```

**EXPLAIN QUERY PLAN Output:**
```
(4, 0, 0, 'SEARCH orders_order USING INDEX sqlite_autoindex_orders_order_1 (id=?)')
```
Plan confirms that the primary key unique B-tree index is utilised for the `id` lookup, with parent verification applied in memory or index filtering.

## 5. Analysis of Likely Failure Modes & Critical Findings

1. **Rate Limiting vs. Capacity:**
   - Without throttle overrides, DRF rate limits (`PUBLIC_CATALOG_RATE = "120/min"`) trigger HTTP 429 within seconds of starting 5+ VUs, resulting in measuring throttle rejection rather than true application throughput. Overriding throttles at the process level isolated pure application latency.
2. **Cold vs. Warm Cache Divergence:**
   - At lower concurrency (1 to 5 VUs), warm cache reduced p95 latency by ~46% on the catalogue read path. Under high load, database locking and serialization dominated over cache lookups.
3. **`link_children_by_phone` Write Load on `GET /api/students/`:**
   - In `schools/views.py`, when a parent queries `GET /api/students/`, the endpoint executes `link_children_by_phone(request.user)`. This issues an `UPDATE schools_student SET parent_id = ...` write query during a read endpoint call. In high-concurrency environments, this introduces row and table locks, degrading read throughput.
4. **Generator Overhead:**
   - Generator CPU stayed between **1.8% and 7.9%** across all test runs on 16 logical cores, confirming that client-side CPU saturation was never a bottleneck.

## 6. What This Baseline Does NOT Tell Us (External Ingress & Network Caveats)

This local benchmark isolates pure Django application server and database query throughput. It does not measure:
1. **Cloudflare Worker & Edge Routing Overhead:** Transit times through Cloudflare edge nodes, SSL termination, and rule evaluation.
2. **Cloudflare Quick Tunnel / Ingress Latency:** Network hops between cloud edge proxies and the origin web service.
3. **Real-World Mobile Network Performance:** 4G/5G mobile carrier packet loss, radio state transitions, latency jitter, and DNS lookup delays.
4. **SMS Gateway Overhead:** Gateway API transit time and telco latency for OTP delivery.
5. **Payment Gateway Overhead:** Razorpay payment page redirection, webhook queuing, and bank gateway processing times.
